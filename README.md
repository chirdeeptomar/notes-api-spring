# NOTES API (Spring Boot)

A Spring Boot 4 + [Elide](https://elide.io/) service for a single `Note` resource (`id`, `body`,
`email`, `createdDate`), exposed over both JSON:API and GraphQL, with schema-per-tenant
multi-tenancy and Prometheus metrics.

This is a port of the sibling Quarkus project at `../notes-api`. Behaviour and endpoint paths are
preserved; see [Differences from the Quarkus original](#differences-from-the-quarkus-original).

- **JSON:API**: `/api/v1/notes` (CRUD), generated by `elide-spring-boot-starter` from the `Note` entity
- **GraphQL**: `/graphql/api/v1` — queries and mutations (`UPSERT`/`DELETE`) over the same model
- **Explorer UI**: `/` — a landing page that switches between Swagger UI and GraphiQL in an iframe
- **API docs**: `/api-docs` (Elide's entity paths) and `/v3/api-docs` (springdoc: entity paths **plus**
  every hand-written `@RestController`)
- **Metrics**: `/actuator/prometheus`
- **Analytics**: `/api/v1/noteStats` — note counts grouped by author email (see [Known gaps](#known-gaps))
- **Search**: full-text search on `Note.body` via `infix`/`prefix` JSON:API filters, backed by Lucene
- **Uploads**: `POST /api/v1/uploads` — multipart upload with a pluggable handler SPI
- **Validation**: `body` and `email` validated on create/update

## Running

The app serves on **port 8081**.

```bash
./gradlew bootRun                                      # default profile
./gradlew bootRun --args='--spring.profiles.active=dev' # dev: seeds 10 mock notes per tenant
./gradlew build                                        # build + run all tests
```

Requires **Java 21**. The build pins a Java 21 toolchain and `org.gradle.java.home`, because
Gradle 8.14's bundled Kotlin compiler cannot parse a Java 25 version string. If you do not have a
JDK at the path in `gradle.properties`, point `org.gradle.java.home` at your own Java 21.

## Multi-tenancy

Each tenant gets its own DB schema. The tenant is chosen by the `X-API-KEY` header:

| Header | Tenant |
|---|---|
| *(omitted)* | `public` |
| `key-a` | `tenant_a` |
| `key-b` | `tenant_b` |
| anything else | `401` |

```bash
curl localhost:8081/api/v1/notes                          # public tenant
curl -H "X-API-KEY: key-a" localhost:8081/api/v1/notes    # tenant_a
```

Tenants are configured under `notes.tenant.*` in `application.properties`. Adding one means
updating **two** places: `notes.tenant.*` and
`spring.jpa.properties.hibernate.search.multi_tenancy.tenant_ids` (which must also list `public`),
or that tenant's search index will not be partitioned.

### How the tenant reaches the database

Worth knowing before changing any of this, because two parts are non-obvious:

1. **Elide's controllers return `Callable`**, so Spring MVC dispatches the actual work to an async
   worker thread. A `ThreadLocal` set in a servlet filter is therefore *not* visible where the data
   access happens. `TenantAsyncConfiguration` (a `CallableProcessingInterceptor`) propagates the
   tenant onto the worker thread and clears it afterwards. Without it, every tenant's traffic
   silently reads the `public` schema.
2. **`SchemaMultiTenantConnectionProvider` resets the schema before returning a connection to the
   pool.** Hikari reuses physical connections, and its own schema reset is inert unless
   `spring.datasource.hikari.schema` is set, so the explicit reset is what stops one tenant's schema
   leaking to the next borrower.

`spring.jpa.open-in-view=true` is pinned deliberately. It is no longer load-bearing for tenancy
(the interceptor handles that), but it is pinned so the dependency is explicit rather than implicit.

## Explorer UI

`/` serves the landing page from `src/main/resources/static/`, copied verbatim from the Quarkus
project's `META-INF/resources`: Swagger UI 5.32.15 (pointed at `/api-docs`) and GraphiQL 5.4.0
(pointed at `/graphql/api/v1`). Static assets, no server-side templating. To query a non-public
tenant in GraphiQL, add `X-API-KEY` in its **Headers** tab.

## Search

`Note.body` is indexed with Hibernate Search. `infix`/`prefix` filters are served from Lucene:

```bash
curl 'localhost:8081/api/v1/notes?filter[notes.body][infix]=needle'
```

Terms must be 3–10 characters (Elide `SearchDataStore` defaults); outside that range the request is
rejected with `400`, which is also how you can tell a query was served by Lucene rather than
falling through to a SQL `LIKE`.

`Note.body` carries `@FullTextField(searchable = Searchable.YES)`. The `YES` is required: Elide's
`fieldIsIndexed()` check tests for it, and the annotation's default silently routes queries to the
plain JPA store instead.

Tests use an in-memory Lucene directory (`local-heap`, set in `tasks.test`) because several
`@SpringBootTest` contexts in one JVM would otherwise contend for the same `write.lock`.

## Differences from the Quarkus original

| | Quarkus | Spring |
|---|---|---|
| Metrics | `/q/metrics` | `/actuator/prometheus` |
| Port | 8080 | **8081** |
| Raw OpenAPI scan | `/q/openapi` | `/v3/api-docs` |

Roughly 300 lines of hand-wired Quarkus code are gone: `AnalyticsDataStoreProducer`,
`RuntimeClassLoaderClassScanner`, its classpath-extraction workaround, `ScannedResourcePaths` and
`ElideSetting`. Elide's Spring autoconfiguration supplies the aggregation store, the controllers and
the OpenAPI document, and springdoc and Elide share one `io.swagger.v3` object model, so the JSON
round-trip the Quarkus version needed to bridge two OpenAPI models is unnecessary.

## Known gaps

**Analytics is not tenant-scoped.** `/api/v1/noteStats` resolves and groups counts by email, but
returns the same data regardless of `X-API-KEY`. `TenantAwareDataSource` is registered as the
`defaultDataSource` bean that Elide's `queryEngine(...)` resolves, but its `getConnection()` is
never called — instrumenting it shows zero invocations, because the bean is declared
`autowireCandidate = false` (needed to stop a second `DataSource`-typed bean making every other
unqualified `DataSource` injection point ambiguous) and so is not injected into `queryEngine`
either. The two `AnalyticsTest` cases are `@Disabled` with this explanation rather than deleted or
weakened.

Fixing it means getting a tenant-aware `DataSource` into the `QueryEngine` without making the
application's other `DataSource` injection points ambiguous — for example by supplying the
`QueryEngine` bean directly instead of letting autoconfiguration build it.
